## Run notes (hand-written; not produced by the generator)

- **Frozen code (primary results).** The `rules` and `hybrid-local-4b` runs used commit `7907c58` from a separate clean worktree, so no in-progress edits were measured. Before freezing, a 3-file end-to-end sanity probe was run that included 2 held-out files. It exposed one extraction bug: on GST invoices, "Date of Supply" is read as the invoice date. That bug was deliberately **not** fixed before these runs. Fixes made after them are listed in `docs/TEST_RESULTS.md` and are not reflected in these two columns.
- **Discarded attempts.** Two earlier `hybrid-local-4b` attempts were stopped and are not reported. In the first, the Docker-hosted llama.cpp container was killed for lack of memory, and 80 records fell back to rules. In the second, the Docker Desktop engine hung. The reported run used the same llama.cpp release (b11580, CUDA build) running natively on Windows, with the same model file and settings. It had 0 LLM fallbacks (see the last row of the summary).
- **Contention.** During the `rules` run (07:28–07:43 UTC), a separate OCR-benchmark process was competing for CPU on the same machine. Timings for the scanned files, including `scale/scanned_100_pages.pdf`, are therefore pessimistic. Accuracy is not affected.
- **Other models.** The 9B model (`hybrid-local-9b`) was not run, by the project owner's decision. Google Gemini was not measured, by the owner's decision ([gemini.md](gemini.md) says why); the overview in [../EVALUATION.md](../EVALUATION.md) puts all runs side by side. The system works with any OpenAI-compatible local model, or with Claude or Gemini (see README › Use your own model). A stronger model generally improves extraction on hard layouts, but it cannot fix OCR misreads, and spreadsheet parsing never uses the LLM.
- **Where time goes on the 1000-page PDF.** Indexing (chunking plus CPU embeddings) is the slowest stage: about 4 pages/s in the frozen `rules` run and about 7 pages/s in `rules-postfix`, after the indexing speed-up in `29118a7` (the whole file took 265 s, then 160 s; the frozen run also had the CPU contention noted above). Parsing runs at roughly 250–280 pages/s and extraction at roughly 75–85 pages/s.
- **Post-fix runs (`rules-postfix`, `hybrid-local-4b-postfix`).** The same dataset, configurations and model, re-run at commit `e922bae` (all final-review fixes, including the "Date of Supply" fix) from a clean worktree. **These columns are not a blind measurement:** at least one of the fixes ("Date of Supply") was found on a held-out file, so the held-out split is no longer fully held out for this code. Read them as "the shipped code on this dataset" and the frozen columns as the fairer estimate. One change between the runs matters for the LLM column: the input budget now follows the model's context window (8192 tokens per slot, minus 4096 reserved for output and 1014 for the prompt, × 3 characters per token = 9,246 characters) instead of the fixed 20,000 characters, so every request fits the 4B server's 8192-token slot.
- **Logs.** Each reported run's log is named under *Run logs* above. The two discarded `hybrid-local-4b` attempts are kept in `eval/results/logs/discarded/` (`hybrid-local-4b-attempt1-docker-oom.log`, `hybrid-local-4b-attempt2-docker-hang.log`).
- **Commit IDs.** IDs such as `7907c58` name the point in the project's development history at which a run was measured (the results files record them under `run.commit`). The published repository holds that work as a single commit, so the IDs identify runs; they are not browsable commits.

## Methodology

**Dataset.** `backend/eval/dataset/` is synthetic: generated by this project's own code (`python -m eval.synth.build`, seed 42). 164 labeled files with 377 records — by kind: corrupt 8, csv 12, jpg 22, pdf 77, png 13, tiff 6, xls 8, xlsx 18; by quality: clean 103, lowres 12, photo 8, scan_heavy 13, scan_light 28; by split: dev 74, heldout 71, na 19. 6 invoice templates (T1, T2, T3, T4, T5, T6) plus `ledger` files. 8 files must fail (corrupt, empty, encrypted or mis-typed); 5 duplicate pairs (an original and a degraded copy); a cross-verification group of 21 files (a ledger and the PDFs its rows describe). Expected issue codes in the labels: CROSS_VERIFICATION_MISMATCH 6, DUPLICATE_INVOICE 5, LINE_ITEMS_SUM_MISMATCH 10, LINE_ITEM_MATH 6, MISSING_FIELD 78, TOTAL_MISMATCH 16. Scale files (run only with `--include-scale` / `--scale-only`): `scale/large_1000_pages.pdf` (1000 pages, 863 records), `scale/scanned_100_pages.pdf` (100 pages, 90 records). Template styles as implemented in `eval/synth/templates.py`: T1 US letter, T2 EU VAT, T3 UK, T4 Indian GST, T5 80 mm receipt, T6 modern two-column. Labels (`labels.json`) are exactly what is printed, normalised; anything not printed is `null`; expected issue codes are derived from the labels.

**Splits.** `dev` = the templates the rules were developed against (T1, T2, T3); `heldout` = templates never used for tuning or debugging the extractor (T4, T5, T6); `na` = template-free files (ledger). See Limitations for what the rules task knew about the held-out templates.

**Pipeline under test.** For each file, in label order: read the bytes, sniff the type from magic bytes exactly as the upload endpoint does (an empty or unsupported file is rejected with its typed code), store it, create the document and job, commit, and process it on the inline queue — the same `process_job` the Celery worker runs, with the same retries. The main set runs in a fresh SQLite database and storage directory, each scale file in its own fresh one; `.env` is ignored so a developer's settings cannot leak in. Results are read back after the whole set, because duplicate and cross-verification flags on earlier documents depend on later uploads.

**Record matching (per file).** 1) by `normalize_invoice_number` equality; 2) by location — overlapping page ranges (intersection over union) or the same sheet row; 3) by order where locations do not contradict. Assignment is greedy by score. Unmatched labeled records are *missed* and all their fields count as wrong; unmatched predictions are *extra* records (reported as record precision; they do not enter field accuracy, and their validation flags are counted separately).

**Field comparison.** Supplier/customer names by `normalize_name` equality (case, punctuation, accents, leading "the" and legal suffixes such as Ltd/GmbH ignored); a fuzzy variant accepts a `rapidfuzz` ratio ≥ 0.9 of the normalised names. Invoice numbers by `normalize_invoice_number` (alphanumerics, upper case). Dates exactly. Amounts and the tax rate within 0.01. Currency exactly. A null label is correct only if the prediction is null too; a non-null prediction there is a **hallucination** (hallucination rate = such predictions / null labels over the nine core fields of matched records). This counts any value put where the document prints none for that field — including a printed value assigned to the wrong field (e.g. a delivery date taken as the missing invoice date), not only invented values. `line_items` counts as correct only when every labeled item is strictly matched and none is extra. **Record exact match** = all nine core fields correct.

**Line items.** Candidate pairs have equal amounts (within 0.01); pairs are taken greedily by description similarity, so two items with the same amount go to the descriptions they resemble. A strict match also needs a description ratio ≥ 0.9 (case and whitespace ignored) and equal quantity and unit price. Precision/recall are micro-averaged over all items; items of missed records count against recall, items of extra records against precision.

**Validation flags.** For `TOTAL_MISMATCH`, `LINE_ITEMS_SUM_MISMATCH`, `LINE_ITEM_MATH`, `MISSING_FIELD`, `DUPLICATE_INVOICE` and `CROSS_VERIFICATION_MISMATCH`: expected codes per labeled record vs the codes on the matched record. A duplicate pair counts as detected when either member carries `DUPLICATE_INVOICE` (the per-code numbers are strict about which one: the later upload). A *clean* record has none of the six codes expected.

**Timing.** Wall clock around `enqueue` (= processing incl. retries) per document, sequential, after a warm-up that imports the pipeline and loads the OCR engine (`rapidocr`) and the embedding model once (a long-running worker pays that once; repeated for each fresh environment). `processing_ms` is the pipeline's own measurement from claim to commit. Pages per second = pages processed / seconds. Indexing (chunking + embeddings with fastembed `BAAI/bge-small-en-v1.5`) is part of the time.

## Limitations

- **The data is synthetic**, generated by this project's own code from 6 templates. It exercises the formats, degradations and error cases the system must handle, but layouts, vocabulary and noise are far less varied than real supplier documents. **Accuracy on real-world documents will differ** — probably lower for layouts unlike these templates and for real scanner and camera noise; these numbers measure the system on this dataset, not in production.
- **What held-out means here.** The held-out templates T4–T6 were never used for tuning — no rule was written or adjusted while looking at them. However, the rules extractor was designed to support their *style categories* (an Indian GST invoice, a receipt, a two-column layout), so the held-out split is blind to the concrete layouts, not to the categories. It is a fairer test than the dev split, not a fully blind one.
- **LLM configurations measured in this report:** `hybrid-local-4b` — configured model `qwen3-4b`; models recorded on the extracted documents: `qwen3-4b`; the server reported `qwen3-4b` (4.02 B params, 2.32 GiB), model file `Qwen3-4B-Instruct-2507-Q4_K_M.gguf`, n_ctx 8192, total_slots 2, build_info b11580-4413a1924; `hybrid-local-4b-postfix` — configured model `qwen3-4b`; models recorded on the extracted documents: `qwen3-4b`; the server reported `qwen3-4b` (4.02 B params, 2.32 GiB), model file `Qwen3-4B-Instruct-2507-Q4_K_M.gguf`, n_ctx 8192, total_slots 2, build_info b11580-4413a1924. Each hybrid result holds only for the model and server it was measured with; one model's numbers say nothing about another (local or cloud), and LLM latency depends on the server and, for cloud APIs, the network.

Configurations not measured in this report (no results file): `hybrid-local-9b` (needs an OpenAI-compatible LLM server at http://127.0.0.1:8080/v1 serving `qwen3.5-9b`); `hybrid-gemini` (needs GEMINI_API_KEY); `hybrid-claude` (needs ANTHROPIC_API_KEY).

- **Ground truth covers six issue codes.** Quality-dependent flags (`LOW_CONFIDENCE`, `OCR_LOW_QUALITY`, `AMBIGUOUS_DATE`, `CURRENCY_INFERRED`, `EXTRACTION_DISAGREEMENT`, ...) have no labels, so the review rate of clean records includes legitimate low-confidence flags on scans.
- **One machine, sequential, SQLite.** Times are for one document at a time on the machine listed under Environment, with SQLite instead of PostgreSQL and no queue overhead; a deployment with several workers processes documents in parallel.
- **Matching is lenient by design** (normalised names, invoice numbers without punctuation, amounts within 0.01); the fuzzy-name and matched-only accuracies are reported next to the strict ones so the effect of the rules is visible.

From `backend/` with the virtual environment active (the commands each run recorded are under Environment):

    python -m eval.synth.build --out eval/dataset --seed 42 --scale
    python -m eval.run_eval --dataset eval/dataset --config rules --include-scale --out eval/results/rules.json
    python -m eval.run_eval --dataset eval/dataset --config hybrid-local-4b --out eval/results/hybrid-local-4b.json

    python -m eval.run_eval --dataset eval/dataset --config hybrid-claude --out eval/results/hybrid-claude.json
    python -m eval.report eval/results/*.json --out ../docs/EVALUATION.md

The hybrid configurations need an OpenAI-compatible LLM server (`qwen3-4b` at http://127.0.0.1:8081/v1 for `hybrid-local-4b`, `qwen3.5-9b` at http://127.0.0.1:8080/v1 for `hybrid-local-9b`) or an API key in the environment (GEMINI_API_KEY for `hybrid-gemini`, ANTHROPIC_API_KEY for `hybrid-claude`); without them the runner refuses to run. Options: `--limit N` (first N files), `--embedding hashing` (fast, not the production embedder), `--ocr-workers N`, `--scale-only`. The scorer is `eval/metrics.py` (unit-tested in `tests/unit/eval/test_metrics.py`); every metric can be recomputed from the committed results JSON and `labels.json`.
